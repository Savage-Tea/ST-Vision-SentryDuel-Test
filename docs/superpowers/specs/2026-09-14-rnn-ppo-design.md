# 阶段③：RNN + PPO 端到端策略 —— 设计

日期：2026-09-14
状态：设计已评审通过，待实现

---

## 1. 背景

前两个阶段的实测结论：

| 阶段 | 做法 | 战力 |
|---|---|---|
| ① | 本回合穷举搜索 + 手工评估 | vs baseline ≈ 0.525，vs hunter ≈ 0.470 |
| ② | MCTS/PUCT | 更慢（≈26 倍）且更弱（10:13 vs 21:10），**已停用** |

两个已知事实决定了本阶段的设计空间：

1. **手工评估函数是当前策略的载体**（"占中心 + 狙击来路"），它也是颜色不对称的来源
   —— 红蓝双方在得分区对峙时红方先手开火必胜，执蓝胜率 0%。
2. **目前的网络在部署路径上根本没被使用**：权重只在 MCTS 根部当先验，而部署默认走
   阶段①的穷举搜索。

本阶段做一个**完全端到端**的策略：网络直接输出动作，不做任何搜索。

---

## 2. 目标与非目标

**目标**

- 一个循环策略网络，直接驱动 `act()`，无搜索、无手工评估、无手工信念
- 完整的自对弈 PPO 训练闭环，可迭代
- 与阶段①**同口径**可比——否则无法判断是否真的更强

**非目标**

- 不针对 baseline / hunter 调参（用户明确定过：优化目标是自对弈强度）
- 不替换阶段①的部署路径。阶段①保持默认，直到策略在同口径评测里真的更强
- 不追求 NPU 加速。这个网络约 34 万参数，瓶颈在自对弈生成的 CPU 负载

---

## 3. 决策记录

四项已确认的选择，连同被否的选项一并记下，避免日后反复。

### 3.1 定位：端到端策略，去掉搜索

**已选**：策略网络直接决策。

**已否**：保留搜索、只替换评估与信念。
**理由**：用户选择端到端。

**已知风险**：本游戏分支因子仅约 7 且完全确定性，纯策略可能打不过浅搜索
（阶段②的 MCTS 已经演示过一次"复杂方法未必更好"）。这个风险已被知晓并接受。
缓解办法只有一个：**同口径评测**。打不过就如实报告，不做事后美化。

### 3.2 信念：去掉手工可达集，纯学习

**已选**：obs 不含手工信念，RNN 的 hidden state 就是信念。

**已否**：先保留手工信念跑通再做消融。
**理由**：用户选择纯学习、天花板优先。

**代价**：若 RNN 学不会追踪敌人，会难以区分"方法不行"与"管线有 bug"。
因此第 12 节的观测一致性测试是**必须先于训练**完成的。

### 3.3 奖励：每回合 Δ 分差 + 终局胜负加成

**已选**：密集奖励。

计分规则（`engine/src/board.cpp`）：

- 击杀命中：`me.score += 2`
- 每个行动阶段结束时，自己在得分区内：`sentry.score++`
- 得分区是中心十字 5 格：`(3,2) (2,3) (3,3) (4,3) (3,4)`

所以每回合的 Δ 分差是 `0 / ±1 / ±2` 量级，比"只在终局给 ±1"密集得多。

**奖励的记在哪一步**（精确的信用分配，不留模糊）：

- 击杀 `+2` 记在**开火那一步**
- 占点 `+1` 记在该方**行动阶段的最后一步**（分数在 `end_side_turn` 结算）
- 终局加成 `胜 +1 / 负 -1 / 平 0` 记在**该方序列的最后一步**

**已否**：只给终局 ±1（一局约 150 步，信用分配过难）；
只用分数不加终局项（会学到"刷分但输掉比赛"）。

### 3.4 rollout 架构：C++ 自对弈 + Python 只做 PPO

**已选**：C++ 跑 rollout 并写轨迹，Python 读轨迹做 PPO 更新。

**已否**：pybind 绑定 sim、Python 驱动批量 rollout。
**理由**：rollout 吞吐差一个数量级；且部署侧仍要写一份 C++ GRU，"两份实现"并没有省掉。

**关键设计**：轨迹**只存动作，不存 logprob**。`old_logprob` 由 Python 用自己的前向
重算。这样手写 GRU 与 torch 之间的微小数值差异**不会**污染 PPO 的重要性比率——
它只需要"行为足够接近"，而这一点由差分测试卡住（第 12 节）。

## 4. 架构与数据流

```
C++ selfplay_ppo ──写──► 轨迹 (.bin) ──读──► Python PPO 更新
  （双方都用当前策略）                          │
       ▲                                        ▼
       └──── make 重编（权重编进头文件）◄──── 导出 policy_weights.h
```

一轮迭代 = 生成轨迹 → 训练 → 导出 → 重编。与现有 `tools/pipeline.sh` 同形，
重编约 1 分钟，相对自对弈生成时间可忽略。

## 5. 观测 obs v3

**与现有 `obs/encode.h`（410 维）是两套**，不要混用。现有编码保持不动，
阶段①继续用它。新增 `obs/encode_v3.{h,cpp}`。

输入必须是**局部视角**状态（我方落在 red 槽位，见 `sim::to_local`），
红蓝共用同一个网络。

### 平面（7 × 49 = 343）

索引 `plane * 49 + y * 7 + x`：

| 平面 | 内容 | 来源 |
|---|---|---|
| 0 | 障碍 | 直接可观测 |
| 1 | 得分区 | 直接可观测 |
| 2 | 我方位置（单热） | 直接可观测 |
| 3 | 我方火力覆盖格 | 由我方位置+朝向完全确定 |
| 4 | 我方视野覆盖格 | 由我方位置+朝向完全确定 |
| 5 | 敌方**当前可见**位置（单热；不可见时全 0） | 直接可观测 |
| 6 | 敌方 last_known_pos（单热） | 引擎提供（规则信息） |

**被移除的**：原平面 3（可达集信念）、平面 5（信念锚点）、平面 7（危险格），
以及"信念规模"标量。这三者都是手工推断，正是本阶段要交给 RNN 的东西。

平面 3/4 保留的理由：二者由我方位置与朝向**完全确定**，是可直接观测的几何，
不是记忆。给出来只是省掉网络重学视野形状的开销，不构成手工信念。

### 标量（17）

| 索引 | 内容 |
|---|---|
| 0–3 | 我方朝向 one-hot（N/E/S/W） |
| 4 | `fire_cd` / 2 |
| 5 | `scan_cd` / 3 |
| 6 | 我方得分 |
| 7 | 敌方得分 |
| 8 | 回合号 `turn` |

交给网络自己学。

## 6. 动作空间与决策粒度

- **决策粒度是「一个行动」，不是「一个回合」。** 引擎每次 `act()` 内最多允许 3 个行动
  （`MAX_ACTIONS_PER_TURN = 3`），所以一局是约 20–25 回合 × 2 方 × ≤3 步 ≈ 150 步。
- **动作空间沿用现有 8 维**（`brain/actions.h` 的 `kActionDim`）：
  `0=move  1..4=turn N/E/S/W  5=fire  6=scan  7=收手`
  这一层已经过验证，不重新发明。
- **hidden 只在我方做决策时推进一步。** 对手的行动不推进——引擎不给我们看对手的过程，
  我们只在下次 `act()` 时看到结果与新观测。
- **hidden 状态跨 `act()` 保持，新对局重置。** 部署侧沿用现有判据
  （`board.turn == 0 || board.turn < last_turn`，见 `agent/act.cpp`）；
  自对弈侧由驱动器显式重置。

## 7. 网络结构

```
obs(360) → Linear(360→128) → ReLU → GRU(input 128, hidden 256)
                                    ├─→ Linear(256→8)   策略 logits
                                    └─→ Linear(256→1)   价值（**线性，不加 tanh**）
```

约 34 万参数。GRU 参数：`3 × (128×256 + 256×256 + 2×256) ≈ 296k`。

### 价值头不加 tanh —— 这是必须的修正

现有 `tools/train_mlp.py` 的价值头是 `tanh`，输出被限制在 `[-1, 1]`。
在本阶段的奖励下这会**直接失效**：每回合 Δ 分差累积到终局，回报量级可达 ±20，
tanh 会长期饱和，价值网络失去分辨能力。

因此价值头用**线性输出**。这是与阶段②网络的实质性差异，不是风格选择。

## 8. C++ 推理与数值一致性

新增 `brain/policy_net.{h,cpp}`，权重由 `tools/train_ppo.py` 导出到
`brain/policy_weights.h`（生成产物，与 `brain/net_weights.h` 并列，进 `.gitignore`）。

接口与现有 `brain/net.h` 同形，但多一个 hidden 状态的读写：

```cpp
namespace brain {
// 单步前向：读入 obs 与当前 hidden，写回新 hidden、策略 logits、价值
bool policy_forward(const float* obs, float* hidden /*kHidden*/,
                    float* policy_logits /*kActionDim*/, float* value);
void policy_reset_hidden(float* hidden);
}
```

**数值一致性不放在关键路径上**（见 3.4）：轨迹不存 logprob，由 Python 重算。
手写实现只需行为接近，由差分测试卡住（第 12 节）。

## 9. 轨迹格式

新增 `selfplay/selfplay_ppo.cpp`。

**核心约束：红蓝双方必须各有一条独立的序列。** 双方共用同一个策略网络
（因为引擎对蓝方镜像、我们 `to_local` 后我方总在 red 槽位），但
**hidden 状态绝不能跨方共享**，否则等于把对手的思考过程灌进自己的记忆。

```
magic    "SDPP"          4B
version  u32 = 1
obs_dim  u32 (= 360)
act_dim  u32 (= 8)
games    u32

每个 game:
  for side in {R, B}:          # 两条独立序列
    steps  u32
    steps 条:
      obs     f32[obs_dim]
      action  u8
      reward  f32
```

**不需要 `done` 标志**：游戏必定在 `turn ≤ 25` 内终局（`brain::is_terminal`），
所以每条序列都以真实终局结束，不存在截断，bootstrap 值恒为 0。

## 10. 训练

新增 `tools/train_ppo.py`。

| 项 | 值 | 说明 |
|---|---|---|
| 算法 | PPO，clip 0.2 | |
| γ / λ | 0.99 / 0.95 | GAE |
| epochs | 4 | 每批轨迹的复用轮数 |
| minibatch | **整局**（不跨局切） | 避免 hidden 串台 |
| entropy bonus | 0.01（可调） | 防过早收敛 |
| lr | 3e-4 | |
| 梯度裁剪 | 1.0 | |
| torch 线程 | 8 | 见下方说明 |

### torch 线程数必须设小

cluster48（192 核）上实测同样 30 步，**机器同时还在跑自对弈**时：

| threads | 192 | 32 | 8 | 1 |
|---|---|---|---|---|
| ms/步 | 385 | 410 | 312 | 71 |

核越多越慢，1 线程反而快 5.4 倍。这是过载的典型形态。所以**显式设小**，
不要用 torch 默认的"用满所有核"。

### 对手池

**只用历史版本自己**（联盟），不把 baseline / hunter 放进训练——遵循
"自对弈优化、不特攻"的约束。这两个模型只用于评测。

### 与 torch 的一致性

`old_logprob` 在 PPO 更新开始时由 torch 用自己的前向重算（在任何一个梯度步之前），
不使用 rollout 侧的值。这样跨实现的数值差异不会进入重要性比率。

## 12. 测试

按"能证伪"的标准写，不是走过场。每条测试都要能被一个已知错误的实现弄失败。

1. **GRU 前向差分测试**（M1 的门槛）：同一权重、同一输入序列，
   C++ `policy_forward` 与 torch 前向逐元素比对。容差按 float32 累积误差定，
   超差即失败。
2. **观测一致性**：训练侧与部署侧共用同一份 `encode_v3`（沿用现有纪律，
   只有一份实现）。加红蓝**等变性**断言：镜像局面下红蓝双方的观测应当等价。
3. **时序测试**：hidden 跨 `act()` 保持；新对局（`turn == 0`）重置；
   红蓝两条序列的 hidden 互不影响。
4. **轨迹格式测试**：写入→读回的 round-trip；字段逐字节比对。
5. **规则差分**：`selfplay_ppo` 驱动的对局必须与真实引擎一致
   （复用现有 `tests/difftest_rules.cpp` 的思路）。

### 验收标准

- 与阶段①**同口径**联盟评测：局数与对手池完全相同
- **必须分色报数**，不接受只看聚合。聚合数字掩盖颜色不对称这件事已经发生过一次
  （聚合 0.525 把"执红全胜 + 执蓝全负"显示成了一个看着中立的数）
- 对上 baseline / hunter 的分色数据
- **若打不过阶段①，如实报告**，不做事后美化

## 14. 风险

| 风险 | 程度 | 缓解 |
|---|---|---|
| **RNN 学不会追踪敌人**（去掉手工信念的直接后果） | 高 | 这是本阶段最大的不确定性。M1 的观测一致性测试是前提；先用小规模跑通再看 |
| 纯策略打不过浅搜索 | 中 | 已知并接受。同口径评测，如实报告 |
| 手写 GRU 与 torch 数值不符 | 低 | 已从关键路径摘除（不存 logprob）；差分测试卡住 |
| 整局 BPTT（~150 步）CPU 开销 | 低 | 网络小；必要时按块截断 |
| 自对弈策略循环/退化 | 中 | 联盟（历史版本池），不用纯当前策略互打 |
